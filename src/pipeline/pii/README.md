# 🛡️ PII Detection Implementation

## 1. Objective

The objective of this implementation is to identify personally identifiable information (PII) within corpus texts and enrich each record with metadata that enables the determination of PII presence, its type, its position within the text, and the proportion of content corresponding to sensitive information.

## 2. Considered PII Types

The following PII types were defined for detection:

- email  
- phone  
- ip  
- physical_address  

## 3. Detection Strategy

PII detection is based on a hybrid approach that combines two complementary methods: structured detection using regular expressions (regex) and contextual detection using the DataFog model.

### 3.1 Regex-based Detection

Regular expressions are used to identify clearly defined structured patterns, such as:

- email addresses  
- phone numbers  
- IPv4 addresses  
- potential physical addresses based on keyword patterns  

This approach allows precise control over pattern matching and facilitates the reduction of false positives through additional validation rules.

### 3.2 DataFog-based Detection

DataFog is employed as a language model-based detection tool, configured with the following engine:
```
DATAFOG_ENGINE = "smart"
```
This method enables the identification of PII entities based on linguistic context, acting as a validation mechanism for detections generated by regex.

## 4. Decision Rule

Final detection is not based on a single method but on cross-validation between both approaches.

A detection is considered valid only if the following conditions are simultaneously satisfied:

- both methods identify the same PII type  
- the corresponding spans overlap within the text  

Formally:

```python
if regex_item["type"] == datafog_item["type"] and spans_overlap(regex_item, datafog_item):
    confirmed.append(regex_item)
```

Under this criterion:

- regex acts as a candidate generator  
- DataFog acts as a contextual validator  
- only mutually confirmed detections are retained  

When both methods agree, the span identified by regex is preserved, as it typically captures the complete structured entity.

## 5. Label Normalization

Since DataFog may return heterogeneous labels, a normalization process is applied to map them to the predefined PII types.

Mappings include:

- email, mail → email  
- phone, telephone → phone  
- ip, ip_address, ipv4 → ip  
- address, location → physical_address  

Labels that do not match the defined categories are discarded.

## 6. Additional Validations

To reduce false positives, specific validation rules are applied:

- Email: must conform to a valid full email format  
- IP: must be a valid IPv4 address (four numeric blocks in the range 0–255)  
- Phone: must contain between 8 and 15 digits; patterns resembling dates or numeric ranges are excluded  
- Physical address: must include keywords such as street, avenue, route, km, neighborhood, passage, or corner, and exclude ambiguous expressions such as "email address", "phone number", "city", or "world"  

## 7. Data Reading

Processing is performed on `.jsonl` files located in:

data/processed

Each file is read line by line, treating each line as an independent JSON record.

Text extraction follows this priority:

text → sentence → content

If no valid textual content is found, the record is processed as empty text.

## 8. Chunk-based Processing

To handle long texts, the input is divided into chunks of up to 1000 characters.

This ensures that:

- words are not split across chunk boundaries  
- positional information is preserved via offsets  
- detections can be accurately mapped back to the original text  

## 9. Detection Flow

The processing pipeline consists of the following steps:

1. record reading  
2. text extraction  
3. text chunking (if necessary)  
4. candidate detection using regex  
5. entity detection using DataFog  
6. comparison of both outputs  
7. filtering based on overlap condition  
8. duplicate removal  
9. metadata computation  

Example:

"Juan lives at calle Cerro Corá 1234 and his email is juan@gmail.com"

Regex detects:

- physical_address: "calle Cerro Corá 1234"  
- email: "juan@gmail.com"  

DataFog detects:

- physical_address: "Cerro Corá 1234"  
- email: "juan@gmail.com"  

Since both methods agree on type and overlapping spans, the detections are accepted.

## 10. Generated Metadata

Each processed record is enriched with the following fields:

### has_pii

Indicates whether at least one confirmed PII detection exists.

### pii_prop

Represents the proportion of text covered by PII:

number of characters covered by PII / total number of characters in the text

Overlapping spans are merged prior to computation to avoid double counting.

### pii_spans

List of confirmed detections, where each element contains:

- type  
- start (0-based index)  
- end (inclusive)  
- text  

## 11. Duplicate Removal

Duplicate detections are removed using the following uniqueness criterion:

(type, start, end, text)

During processing, the same entity may be detected multiple times (for example, due to chunk-based processing). To prevent redundant counting, detections that match in type, position, and content are considered duplicates and removed.

## 12. Output Writing

After processing, the `.jsonl` files are overwritten with updated records.

To ensure data integrity:

1. results are first written to a temporary file (.tmp)  
2. the original file is replaced with the temporary file  

## 13. Generated Report

A global report is generated at:
```
outputs/report/pii_report.json
```
The report includes:

- total number of processed files  
- total number of records  
- number of records containing PII  
- percentage of records with PII  
- detection counts by PII type  

## 14. Final Result

The implemented pipeline enables:

- automated processing of large-scale JSONL datasets  
- PII detection using combined structured and contextual methods  
- validation of detections via span overlap  
- significant reduction of false positives  
- generation of structured metadata for downstream analysis  
- production of global statistical reports

## Conclusion

The implementation follows a precision-oriented approach, where a detection is accepted only when both regex-based and model-based methods agree.

This strategy reduces false positives and produces more reliable outputs, suitable for manual evaluation and data quality analysis.
